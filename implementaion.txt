Implementation Plan — Final Version
What The System Does

User inputs a scenario in plain language. System retrieves relevant historical context from curated hosted pages via Tavily. LLM estimates ODE parameters from that context. ODE engine simulates health and energy trajectories forward. Results are plots and JSON outputs.

Ground truth validation runs separately on past known events to prove the system is accurate before trusting future predictions.

Tech Stack
Language:          Python 3.11+
ODE Solver:        Custom RK4 (NumPy)
LLM:               Claude API (claude-sonnet-4-6)
Web Retrieval:     Tavily API (1000 free calls/month)
Knowledge Graph:   NetworkX (local, saved as .gexf)
Data Processing:   pandas, numpy
Output:            matplotlib (plots), JSON, CSV
Hosting:           GitHub Pages (static HTML, free)
Config:            python-dotenv
Testing:           pytest
Version Control:   Git + GitHub

Knowledge Graph — What It Stores

Tavily handles text retrieval. The knowledge graph handles structured causal chains that don't exist anywhere on the web in queryable form.

NODES:
  Region        → "UK_Yorkshire", "UK_SouthEast"
  PowerPlant    → "Drax_Unit1", "Ratcliffe_on_Soar"
  PolicyEvent   → "UK_Coal_Phase_Out_Announcement_2015"
  EnergyEvent   → "Drax_Unit1_Closure_April_2023"
  PollutionEvent→ "PM25_Drop_Yorkshire_Oct_2023"
  HealthEvent   → "Respiratory_Admissions_Drop_Q1_2024"
  TimePeriod    → "2023_Q2", "2023_Q4"

EDGES:
  PolicyEvent  -[TRIGGERED]->   EnergyEvent
  EnergyEvent  -[PRECEDED]->    PollutionEvent   (lag: 6 months)
  PollutionEvent-[PRECEDED]->   HealthEvent      (lag: 3 months)
  Region       -[DOWNWIND_OF]-> Region           (Psi source)
  PowerPlant   -[LOCATED_IN]->  Region

This gives the LLM structured answers to questions like:
"What happened to health outcomes 9 months after a similar plant closure?"

The Complete Pipeline — Step By Step
Phase 1 — One Time Setup (you run these once)
STEP 1: Download raw data
  → National Grid ESO CSVs
  → NHS HES data
  → DEFRA air quality CSVs
  → Save to data/raw/

STEP 2: Run scripts/prepare_ground_truth.py
  → Cleans raw CSVs
  → Extracts observed X and H values per quarter
  → Saves to data/ground_truth/uk_coal_phaseout.json

STEP 3: Run scripts/build_knowledge_graph.py
  → Reads events_timeline.json
  → Builds NetworkX graph
  → Saves graph.gexf

STEP 4: Run scripts/build_hosted_pages.py
  → Converts raw data into readable HTML pages
  → Saves to hosted_data/

STEP 5: Push hosted_data/ to GitHub Pages
  → Tavily can now search these URLs
Phase 2 — Every Simulation Run
STEP 1: User inputs scenario
  "What happens if UK closes all remaining
   gas plants by 2027 in Yorkshire?"

STEP 2: rag/retriever.py runs
  → Tavily searches allowed URLs with scenario as query
  → Returns relevant content (energy data, health data,
    paper excerpts, policy context)
  → NetworkX graph queried for similar past events
    and their causal chains
  → Both results combined into context block

STEP 3: llm/estimator.py runs
  → Sends to Claude:
      - User scenario
      - Tavily retrieved content
      - Graph query results
      - Parameter schema
      - System prompt
  → Claude outputs 30 parameters as JSON

STEP 4: llm/validator.py runs
  → Checks all ranges valid
  → Clamps out-of-range values
  → Returns clean parameter dict

STEP 5: core/runner.py runs
  → Loads initial conditions
  → Passes parameters to ODE engine
  → RK4 integrates 18 coupled ODEs forward
  → Returns trajectory JSON

STEP 6: Outputs generated
  → outputs/trajectories/scenario_name.json
  → outputs/plots/trajectory_plot.png
  → outputs/plots/scenario_comparison.png
Phase 3 — Validation (runs separately)
STEP 1: validation/backtest.py runs on past event
  → Takes Drax closure 2023 as input
  → Runs full pipeline
  → Gets predicted trajectories

STEP 2: validation/metrics.py runs
  → Loads ground_truth/uk_coal_phaseout.json
  → Compares predicted vs actual
  → Calculates MSE and trajectory error

STEP 3: validation/weight_adjuster.py runs
  → If retrieval led to accurate prediction →
    those graph nodes weighted higher next time
  → If retrieval led to poor prediction →
    those graph nodes weighted lower

STEP 4: Results saved
  → outputs/results/backtest_metrics.csv

What I Found
india_yearly_full_release_long_format.csv: 17,214 rows, India/state-year energy data for 2019-2024. It covers capacity, electricity generation, and power-sector emissions across 38 states/UTs.
Global-Coal-Plant-Tracker-July-2026.xlsx: structured coal-unit dataset. It has 14,674 global unit rows, 1,996 India rows, 52 columns, plant/unit status, capacity, location, ownership, fuel type, retirement/planning fields, and emissions fields.
Weak coupling...Delhi-NCR...pdf: 9-page scientific PDF. Important claim for the graph: crop-residue burning in Punjab contributed only about ~14% of Delhi-NCR PM2.5 during Oct-Nov 2022, implying weak coupling and the importance of local/regional controls such as GRAP.
AQI API: the .env has AIR_QUALITY_API_KEY_INDIA, but the code does not load or use it yet. The likely source is India’s official OGD/data.gov.in real-time AQI resource from CPCB/MoEFCC, which provides hourly AQI from monitoring stations across India (data.gov.in AQI resource). I tried a live probe; the endpoint timed out once and then returned 502 Bad Gateway, so the key is present but not runtime-validated yet.
Current MVP Gap
Right now the project is UK/Yorkshire-oriented. The runner hardcodes UK region inference, retrieval is Tavily plus local HTML keyword search, and the “knowledge graph” is a small NetworkX/GEXF graph. There is no real vector DB, no Neo4j, no durable document ingestion, no chunk store, and no GraphRAG retrieval planner yet.
Target Architecture
We should convert this into a proper India-capable GraphRAG system:
1. Source Layer
   - Local files: CSV, XLSX, PDF.
   - Live APIs: India AQI API.
   - Optional future sources: health admissions, Census/population, meteorology, wind/transport, policy notifications.
2. Ingestion Layer
   - CsvEnergyIngestor for state-year energy mix/emissions.
   - CoalPlantTrackerIngestor for plant/unit-level coal infrastructure.
   - PdfStudyIngestor for scientific reports.
   - IndiaAqiClient for real-time AQI station observations.
   - Every ingested item gets source provenance, timestamp, checksum, schema version, and citation metadata.
3. Document Processing
   - PDF: split by title/section/paragraph, then semantic chunks around 600-1,000 tokens with overlap.
   - CSV/XLSX: do not chunk raw rows blindly. Convert into structured “facts”:
     - India Total 2024 coal generation = ... GWh
     - Maharashtra operating coal capacity = ... MW
     - Delhi 2024 fossil generation share = ...
   - AQI API: normalize station observations into city/state/time/pollutant/AQI records.
4. Vector DB
   - Recommended: Qdrant for local/prod readiness, metadata filtering, and hybrid search.
   - Collections:
     - document_chunks
     - structured_facts
     - scientific_claims
     - scenario_cases
   - Embeddings:
     - Use OpenAI embeddings or local sentence-transformer depending on cost/privacy.
   - Metadata filters:
     - country, state, city, year, source_type, fuel, pollutant, plant_status, metric.
5. Neo4j Knowledge Graph
   Main node types:
   - Country, StateUT, City, Station
   - Plant, CoalUnit, Owner
   - Fuel, EnergyMetric, EmissionMetric
   - AQIObservation, PollutantObservation
   - Study, Claim, Policy, HealthOutcome
   - Scenario, ParameterEstimate, SimulationRun
   Main relationships:
   - (:StateUT)-[:PART_OF]->(:Country)
   - (:CoalUnit)-[:LOCATED_IN]->(:StateUT)
   - (:CoalUnit)-[:USES_FUEL]->(:Fuel)
   - (:EnergyMetric)-[:MEASURED_FOR]->(:StateUT)
   - (:AQIObservation)-[:RECORDED_AT]->(:Station)
   - (:Claim)-[:SUPPORTED_BY]->(:Study)
   - (:Claim)-[:ABOUT_REGION]->(:StateUT|City)
   - (:Plant)-[:CONTRIBUTES_TO]->(:EmissionMetric)
   - (:EmissionMetric)-[:ASSOCIATED_WITH]->(:PollutantObservation)
   - (:Scenario)-[:USES_EVIDENCE]->(:Claim|EnergyMetric|AQIObservation)
6. GraphRAG Retrieval Flow
   For a user question:
   - Parse intent: factual answer, comparison, scenario, simulation, policy, health, plant lookup.
   - Extract entities: state, city, year, pollutant, fuel, plant, policy, health condition.
   - Retrieve from vector DB for semantic context.
   - Query Neo4j for exact entity relationships and numeric facts.
   - Pull live AQI if the user asks for current air quality.
   - Rerank evidence.
   - Build a compact context pack:
     - top semantic chunks
     - graph paths
     - structured numeric rows
     - live API readings
     - citations/provenance
   - Generate answer with citations, confidence, and caveats.
   - For scenario questions, pass retrieved evidence into parameter estimation and simulation.
7. Generation Layer
   Answers should be able to handle:
   - “What is India’s coal dependency trend?”
   - “Which Indian states have the most operating coal capacity?”
   - “How does Delhi AQI relate to Punjab/Haryana crop burning?”
   - “What happens if Chhattisgarh retires 30% coal capacity by 2030?”
   - “Compare Gujarat and Maharashtra fossil generation and AQI.”
   - “Which evidence supports the transboundary pollution assumption?”
8. Simulation Upgrade
   - Replace hardcoded UK_Yorkshire inference with a region resolver for India states/cities.
   - Compute x0 from real fossil share/emissions/AQI instead of defaults.
   - Estimate coupling from adjacency, wind/transport evidence, and graph relationships.
   - Store every run as SimulationRun in Neo4j with linked evidence and parameters.
